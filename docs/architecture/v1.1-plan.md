# UntrashOS 1.1 — plan

Status: in progress.  Done (2026-10-23): item 0, the release key, item 8,
the default network name (untrash, untrash-2, ...), item 7, item 1 and item 6; 2026-10-24 items 2+3 (mesh, address book, co-op, off-site mirror); 2026-10-25 item 4 (NAS side of the UntrashApp) and item 5 (office bridge).  Work items as agreed with the operator, with the
design proposed for each, the order of work and the open decisions.

Platform limits that shape every item: Cortex-A9 dual core, about 700 MiB
usable RAM (`0x04000000–0x2fffffff`), kernel `CONFIG_HZ=100` (10 ms timer
granularity), one passive buzzer on PWM5 (one square-wave voice).

## 0. Repository split — done

Done 2026-10-23: this repository (P4R4D16M4/UntrashOS) plus `board/nas542`
in ZyxelUntrash (branch v1.1); the slot built from the split layout is
byte-identical to the one before.  Contract: `docs/board-interface.md`.
Original proposal: UntrashOS (the operating system) and the per-device
firmware are separate repositories, so a later QnapUntrash reuses the OS.

- `UntrashOS` (new repo): everything device-independent — Desk, design
  system, i18n, services, mesh, update client, image build (mkosi), slot
  format and signing tools, tests.
- `ZyxelUntrash` (existing repo, NAS540/542): kernel patches and configs,
  DTB, loader, PFE firmware extraction, PartnerKey installer and stock
  restore, board services (MCU power, buzzer PWM5, fan, LEDs, bays,
  COPY/RESET buttons, RTC, watchdog), stock data takeover.  It includes
  UntrashOS as a git submodule pinned to an UntrashOS tag — no copy, so
  the OS never drifts between firmware repos.
- Board interface: the OS calls hardware only through a small, documented
  board layer (`/usr/lib/untrash/board/<hook>` + `board.json`: buzzer,
  LEDs, fan, power schedule, bays, buttons, update channel).  A firmware
  repo provides the implementation.
- Releases: an update file contains kernel + DTB + rootfs and is therefore
  device-specific; it is built and released by the firmware repo
  (UntrashOS tag + board layer).  The NAS checks the releases of its own
  firmware repo (`board.json` → `releases`).

logs, mails, previews and the user guide; typed confirmations are DELETE,
FORMAT, KEEP in every language.  Checked by a round trip through i18n.js and

Original plan:

- Replace the German literals in HTML/JS/Python by their English text

- Installer, loader console output, log lines, unit descriptions, file names
  and operation words (button labels, job names, state names) are English
  only; the UI stays translatable.
- Test: a check that fails on non-ASCII letters outside `i18n/*.json`, the

## 7. Desk themes — done

Done 2026-10-23 as planned below; the colour choices are checked by
`design/tests/test_themes.py` (docs/architecture/untrash-design.md, themes).


`design/untrash.css` is dark only and keyed on `--ut-*` tokens.

- `<html data-theme="dark|light|contrast">` plus an orthogonal
  `data-cvd="none|protan|deutan|tritan|achroma"` for colour-vision
  deficiencies; each overrides only tokens.
- Colour-vision variants change the status and chart colours (ok/warn/error,
  RAID states, disk bars) to pairs that stay distinct for that deficiency,
  and always add a second cue (icon or pattern), never colour alone.
- `contrast`: WCAG AAA text contrast, thicker focus rings and borders, no
  glass/blur, no wallpaper behind windows.
- Optional "follow the system" (`prefers-color-scheme`,
  `prefers-contrast`), and reduced motion via `prefers-reduced-motion`.
- Stored per user on the NAS (so it follows the user across browsers), with
  `localStorage` only as a pre-login cache to avoid a flash.
- The wallpaper and logo get a light variant derived from the base graphics.

## 1. Update download from GitHub — done

Done 2026-10-23: image/rootfs/usr/lib/untrash/untrash-update, release
source per board (board.json), tests image/tests/test-update-host.py.
The release key is in place; publishing: firmware docs/build.md.
Original plan:


The upload path already checks the signature (`zt-sig`, keys in
`/usr/lib/untrash/keys/*.pub`) and payload hashes, writes the inactive slot
and lets the loader fall back after three failed boots.

- `untrash-update-check` (timer, daily + "check now" button): reads the
  GitHub Releases API of the project repo (`project.json` gets a `releases`
  URL), picks the newest non-draft, non-prerelease release whose tag is
  newer than the running version (opt-in "beta channel" includes
  prereleases).
- Downloads the `.utslot` asset with resume to the data volume, checks size,
  signature and hashes **before** it is offered.  GitHub is only transport;
  trust comes solely from the signature.
- Desk notification "UntrashOS x.y ready to install" with release notes;
  installation only after an admin confirms (existing `update_install`).
  Optional: "install at next scheduled restart".
- Release signing key: a dedicated release key (offline), separate from
  `untrash-dev`; 1.1 ships both public keys, later releases can retire the
  dev key.  Rollback protection: the manifest's version must be newer unless
  the admin explicitly chooses a downgrade.
- No telemetry: one anonymous HTTPS GET per day, documented.

## 6. Sound editor (timeline) — done

Done 2026-10-23: desk sound-render.js (score model, renderer, motifs) and
the editor in desk.js; tests test_sound_render.js, test-sound-host.py.
The buzzer driver plays exact durations (busy-wait), 100..4000 Hz and at
most 1000 ms per write; untrash-sound splits longer notes and plays tied
parts without gaps.  Original plan:


Current editor: a note list with Hz/ms numbers and a tempo factor.  The
buzzer plays one square-wave voice; steps shorter than 10 ms are not useful.

- Timeline/piano-roll: a palette of note blocks (pitch names, not Hz) and
  ready-made motifs (chime, rise, fall, alarm, trill) that are dragged onto
  one track; blocks can be moved, stretched at the edge (length snaps to a
  grid: 1/16 … 1/1 at the song tempo) and duplicated.
- Loops: a pattern can be repeated n times (like early loop-based music
  programs); the pattern is edited once.
- Modulation the buzzer can do, rendered into the existing `[hz, ms]` list
  in steps of at least 10 ms: slide (glide from pitch to pitch), vibrato
  (depth, rate), arpeggio, staccato/legato (gap length), and a "fade" that
  is a pitch drop since the buzzer has no volume.
- Scale/key selector so dragged notes snap to a scale; tempo in BPM.
- Preview in the browser with the same 10 ms quantisation as the NAS, so
  what you hear is what the buzzer plays; "play on NAS" stays.
- Storage: the editor keeps its own score (blocks, patterns) next to the
  rendered notes; old sound sets still import.  The backend and
  `untrash-sound` stay unchanged except for a higher note limit.

## 2. UntrashMesh (LAN and WAN) — core and co-op mode done

Done 2026-10-24: image/rootfs/usr/lib/untrash/untrash-mesh (daemon + CLI),
Desk window, tests image/tests/test-mesh-host.py.  Kernel: WireGuard, CIFS
client and NBD as modules (firmware repo, kernel/config/system.config;
built-in changes: ARM BLAKE2s, keyrings; needs a hardware run).

Modes (operator decision 2026-10-24):

- **Co-op** (done): a node offers chosen shares to a member, read only or
  read/write (Samba account per partner, sections only from the mesh
  prefix); the member mounts them (CIFS over the mesh) as partner volumes
  /p-data/<partner>-<share>, on which its admin makes shares for its own
  users.  Partner volumes are never offered on (no chains).
- **Extended RAID**, mirror first (off-site mirror done 2026-10-24, PC
  tests only): a data volume gets a RAID 1 copy on a partner.  DRBD 8.4
  (in-tree, `CONFIG_BLK_DEV_DRBD=m`; drbd-utils 9.22, `drbdadm-84`) over the
  mesh, protocol A with `on-congestion pull-ahead`, so local writes never
  wait for the line; DRBD's bitmap sends only what changed while the
  partner was away.  Chosen over NBD + md write-mostly because an md
  member that drops out over a WAN link needs a manual re-add, and md's
  superblock would change the stock volume format.
  - Volume format unchanged: external metadata in a file on the state
    (`/state/mirror/<id>.meta`, loop device); the volume stays a plain
    stock md/LVM/ext4 volume and mounts directly without the mirror.
  - Consent: the owner asks (`/v1/mirror`, resent until acknowledged), the
    partner's admin agrees and chooses a volume; the copy is a sparse file
    `<volume>/.untrash-mirror/<id>.img`; the partner is never primary.
  - Start: at the next mount (untrash-import-zyxel `mount_volume` →
    `untrash-mesh mirror-up`), never on a mounted volume.  If DRBD does not
    start, the volume is mounted directly and the copy marked `bypassed`;
    once connected again the daemon runs `invalidate-remote` (full resync).
  - Never: the volume of the running system (ways B/C, `/run/untrash/host`).
  - End: either side; a member that leaves or is removed takes its mirrors
    with it.  DRBD config per resource, floating sections keyed by mesh
    address; port 7800 + minor.
  - Open: a run on two NAS (dev NAS + untrash-2; needs an authorized
    hardware run).  Tested: fake-DRBD flow (test-mesh-host.py), config
    against the real drbdadm-84 parser.  At shutdown,
    `/usr/lib/systemd/system-shutdown/untrash-mirror` takes the resources
    down after the file systems are unmounted (not yet run on hardware).
  Capacity pools (RAID 0/5 over several NAS) later, LAN only and with a
  clear warning.

Original plan:


- Transport: WireGuard (`CONFIG_WIREGUARD=m` in the system kernel; the
  loader is not touched).  One `ut-mesh` interface, an address from a
  private ULA /64 derived from the mesh id; each node's address derived
  from its public key.
- Membership: a mesh has an id and a member list signed by the admins'
  node keys.  Pairing: one node shows a short code/QR, the other enters it;
  the code carries the mesh id, the inviter's key and current endpoints and
  is valid for minutes.
- LAN: nodes find each other by mDNS (avahi already in the image) and use
  the LAN endpoint directly.
- WAN: UDP port via UPnP/NAT-PMP (miniupnpc already in the image) or a
  manual port forward; a node behind CGNAT reaches others through any
  member with a reachable port (relay).
- Services over the mesh: SMB/WebDAV access to shares by permission, backup
  targets ("off-site backup at a friend's NAS"), Desk access from outside.

## 3. Mesh address book (decentralised name resolution) — done

Done 2026-10-24 as described; names via an /etc/hosts block instead of a
resolved stub zone.


Goal: no static IP, DynDNS or central server needed.

- Each node owns a record `{node key, name, endpoints[], seq, time}` signed
  with its node key.  On any address change (netlink event, UPnP external
  address, periodic check) it increments `seq` and pushes the record to
  every member.
- Every member stores the newest record per node (highest `seq`, valid
  signature) and **forwards** records it has not seen (gossip), so a change
  reaches nodes that were offline or unreachable from the changed node.
- WireGuard roaming helps: when a node with a new IP sends any packet to a
  peer, the peer learns the new endpoint at once; the address book covers
  the reverse direction.
- Failure case both sides change IP at the same time: recovered through any
  third member, the UntrashApp (it is a member, see 4) or an optional
  fallback endpoint (DynDNS name) — documented, not hidden.
- Names: `<node>.mesh` resolves on every member (a resolved stub zone
  served from the address book).

## 4. UntrashApp (companion)

NAS side done 2026-10-25 (PC tests only; no app exists yet).  Contract:
`docs/architecture/app-api.md` (API version 1).  Pairing by QR code in
the Desk (UntrashMesh → Pair the UntrashApp, encoder `desk/qr.js`, checked
against the standard's tables and a separate decoder); the app is linked
per NAS to one Desk user; Ed25519-signed requests over the mesh only;
sign-in modes password / password or app / password and app (number
matching); app confirmation for the listed actions in mode "both"; lost
phone: admin reset, RESET button for admin.

Original plan:

- The app is a mesh member with its own key and the same address-book
  push, so it is an always-moving node that also helps others find each
  other.
- Pairing by QR code shown in the Desk (admin) — the same pairing as
  between NAS nodes.
- Authentication: the app's key can approve a Desk login (push request,
  confirm on the phone) or act as a second factor; admin actions such as
  "install update" can require app confirmation.
- Configuration: the app uses the same JSON API as the Desk over the mesh.
- A versioned, documented API description (`docs/architecture/app-api.md`)
  is the contract between the two projects.

## 5. Document server (office bridge)

Done 2026-10-25 (PC tests only, no real office server tried yet): both
steps, see `docs/architecture/office.md`: Settings → Office (office server,
WOPISrc base), Files → Open in Office, WOPI host under /wopi in
untrash-desk (CheckFileInfo, GetFile, PutFile, locks; tokens bound to user
and file, share rights checked on every request).

Original plan:

Decision 2026-10-22: the NAS stores the documents, an office suite running
elsewhere edits them (e.g. Collabora Online / Nextcloud Office or ONLYOFFICE
next to a Nextcloud).  Collabora/OnlyOffice need several GiB RAM and do not
run on this board.

- Step 1, no new NAS service: Nextcloud mounts NAS shares as "External
  storage" (WebDAV or SMB, both already in UntrashOS); Nextcloud Office then
  edits files that live on the NAS.  Documented in the manual.
- Step 2, WOPI host on the NAS: `untrash-desk` implements the WOPI host
  endpoints (CheckFileInfo, GetFile, PutFile, Lock/Unlock) for files the
  user may access; the admin enters the office server URL once; in Files,
  "Open in Office" opens the document in that editor.  Access tokens are
  short-lived and bound to user + file; share rights apply unchanged.
- Over UntrashMesh the office server can sit at a friend's or in the
  office without open ports.
